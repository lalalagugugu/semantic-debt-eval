## 三种作答方式

我按 Anthropic 在《Building effective agents》（2024）里的区分来定义：流程由代码预先写死的是 workflow；由模型自己决定下一步做什么、调用什么工具、什么时候停的，才叫 agent。照这个定义，第一期的直答不是 agent，它是一条固定流程。

| 名字 | 单元代号 | 模型能做什么 | 谁决定流程 | 期 |
|---|---|---|---|---|
| 直答 | 无后缀，如 SQL-L1 | 读上下文，一次写出查询。执行报错时，harness 把报错发回让它修一次 | 代码（固定流程） | 第一期 |
| 探查 agent | 后缀 -E，如 SQL-L1-E | 在直答的基础上多一个只读工具 run_sql：可以查枚举值、看样例行、试跑查询，最多 8 步后交卷 | 模型（ReAct 循环） | 第一期 |
| 规划 agent | 后缀 -P | 先拆步骤；可以用 Python 做统计；按需检索语义文档，而不是整份放进上下文；经 MCP 调用工具 | 模型 | 第二期 |

v4 回复里「先治理还是先做 agent」用词不准。准确的说法是：先投入治理，还是先投入 agent 能力（工具和多步）。

## 三个栈与单元格

共 17 个中文单元，另加 2 个英文锚点（R-EN、L1c-EN）。

| 栈（agent 写什么） | L0 | R | L1 | L1 调优 | L1.5W 明细宽表 | L1.5S 汇总层 | L2 | L2 调优 | 探查 agent |
|---|---|---|---|---|---|---|---|---|---|
| SQL | 测 | 测；另有英文锚点 | 测 | 测；另测 L1c（Cube 文档原样）及其英文锚点 | 测 | 测 | 测：经 Cube 的 SQL 接口，用 MEASURE() 调用指标 | — | L0-E、L1-E、L2-E |
| 指标层 JSON（Cube） | — | — | — | — | — | — | 测：只能调用已定义的指标，答不了就拒答 | — | — |
| DAX（Power BI Desktop） | 测 | — | 测；另测 L1 原生格式 | — | — | — | 测：度量值 | 测 | — |

- **L1.5W 明细宽表**：按主题把事实表和维度表预先关联好的视图（线上销售、全渠道销售、当前库存、计划、销售目标），只加行级派生列（净额、毛利、是否打折、客户地理、门店地理），不做聚合。按国内数仓分层，这是 DWD 宽表；也是不少问数产品推荐的「大宽表」接法。原始表仍然可见。
- **L1.5S 汇总层**：按主题、固定粒度预先汇总的表，相当于数据中台对外开放的 DWS/ADS 层，例如「门店 × 品类 × 月」的全渠道销售、客户主题汇总（首购日、末购日、订单数）、「门店 × 月」的目标与实际。agent 只看得到这些汇总表和维度表，明细事实表不可见。汇总表的设计见下一节第 5 条。超出汇总表覆盖的问题，正确的行为是拒答；题集冻结前给每道题标「汇总层能否回答」，报告分开列。
- **SQL 的 L2**：和指标层 JSON 用同一个 Cube 模型、同一个引擎，只有接口不同（见 C6）。方言从 ClickHouse 变成 Postgres，查询对象从表变成 Cube 的数据集；这就是这类产品在现实中的样子，如实记录。
- **探查 agent（-E）**：上下文和直答单元相同，另给只读的 run_sql（每次最多返回 50 行、30 秒超时、最多 8 步）。L0-E 和 L1-E 在 chDB 上查；L2-E 的 run_sql 走 Cube 的 SQL 接口。只放在 SQL 栈，因为它要回答的是「治理能否被 agent 替代」，不是语言问题。
- **为什么加 L2-E**：它回答的是「指标都编码好以后，会查数据还有没有用」。我的预判是收益小于 L1-E：探查能找回的是枚举值、连接键这类可从数据发现的知识，L2 已经提供了大部分；剩下的是筛选值（比如同城几家门店的确切名字）和自查结果是否合理。花约 19 元把预判变成数字，值得。
- **DAX L1**：代表「问到的指标恰好没有度量值」，即超出报表覆盖范围的即席问题。
- **DAX L1 原生**：信息与 DAX-L1 相同，但不经过 YAML，直接给 agent 看 PBIP 项目里的 TMDL 文件（表、列、描述、关系）、同义词和 AI instructions 原文。它和 DAX-L1 之差，就是呈现格式本身的影响（C10）。

哪些对比是干净的：同一栈内纵向比，看治理、宽表、汇总层、编码、调优各值多少；L1 和 L2 上横向比 SQL 与 DAX，两边信息相同；L2 上比三种接口；同一档位比直答与探查 agent；DAX-L1 上比 YAML 与原生格式。英文锚点只用来和 Cube 公布的数字对照。

## 档位定义与呈现方式

档位按内容定义，与栈无关。

| 内容 | L0 | R | L1 | L1 调优 | L1.5W 明细宽表 | L1.5S 汇总层 | L2 |
|---|---|---|---|---|---|---|---|
| 表名、字段名 | 晦涩缩写 | 业务名（Contoso 原样） | 业务名 | 同 L1 | 同 L1，另加宽表 | 只有汇总表和维度表 | 同 L1 |
| 关系 | 约三分之二 | 无 | 全部，含基数和用途 | 同 L1 | 同 L1 | 汇总表到维度表 | 同 L1 |
| 技术字段 | 暴露 | 无 | 不提供 | 同 L1 | 同 L1 | 不提供 | 同 L1 |
| 字段描述（粒度、单位、何时使用） | 无 | 无 | 有 | 可补充 | 同 L1，另有宽表列描述 | 汇总表的粒度、列描述、可加性 | 同 L1 |
| 枚举值含义 | 无 | 无 | 有，来自数据探查 | 同 L1 | 同 L1 | 同 L1（在维度表上） | 同 L1 |
| 同义词与企业约定 | 无 | 无 | 有，来自约定清单 | 可补充 | 同 L1 | 同 L1 | 同 L1 |
| 指标口径 | 无 | 无 | 文字公式 | 可补充 | 文字公式 | 文字公式；常用的已算成列 | **可调用的指标**，文字保留为描述 |
| 行级逻辑（净额、毛利、是否打折、当前库存） | 无 | 无 | 文字 | 文字 | **做进宽表** | 做进汇总 | 做进指标层或度量值 |
| 聚合 | agent 自己写 | 同左 | 同左 | 同左 | 同左 | **按固定粒度预先算好** | 引擎按指标定义算 |
| 示例（问题 → 查询） | 无 | 无 | 无 | 有 | 无 | 无 | L2 调优才有 |

五条规矩保证对比干净：

1. L0 只改名、删描述和部分关系、加几列技术字段，不动数据行，参考答案不变。SQL 和 DAX 用同一套改名和删除。
2. L1 由一个看不到题目的 agent 根据表结构、数据探查和约定清单写成。
3. L1.5W 只把 L1 文字里已经定义的行级逻辑做进宽表；L1.5S 只汇总 L1 文字里已经定义的指标；L2 只把 L1 文字里已经定义的指标做成对象。这样各档之差只来自「编码了多少」，而不是多写了口径。
4. 同一份指标清单同时生成 DAX 度量值和 Cube 指标。
5. 汇总层按「常规经营报表需求」设计：同一个看不到题目的 agent 先写一份需求清单（哪些报表、什么粒度、哪些指标），你过目后再建表；比率存分子和分母，去重计数标明不能再相加。这模拟的是数仓团队按报表需求建 ADS，而不是按问数需求建。

### 统一 YAML 与原生格式对照

所有自建单元的 agent 读同一份 YAML，栈之间只差物理名和一段等长的语法说明。YAML 不绑定任何查询语言；栈只决定 agent 用什么语言写查询、在哪个引擎上执行。这样 SQL 与 DAX 的对比里就没有「呈现格式」这个混杂变量。业界也在朝这个方向走：Snowflake、dbt Labs、Databricks、Salesforce 等在推的 Open Semantic Interchange（OSI）就是一个厂商中立的语义模型规范，我们的 YAML 结构参考它，最终报告会专门讨论。两个例外：英文锚点和 L1c 原样使用 Cube 的建表语句和文档，因为它们的用途就是复现。

统一 YAML 拿掉的是「产品怎么把语义模型呈现给模型」这一层，不是产品的表达能力。表达能力上的限制在执行时都保留：DAX 的关系模型（两张表之间只能有一条激活的关系）、Cube 能定义什么样的指标、JSON 接口不能在指标结果上再算一步。而且 L1 的每类信息在 Power BI 里都有原生的存放位置（描述、同义词、AI instructions），YAML 并没有替 Power BI 多带信息。呈现格式本身的影响由 DAX-L1 原生单元量出来。SQL 侧不做这个对照，因为数据库没有可比的「产品格式」。

L1 和 L2 里 agent 看到的内容大致如下（每个单元只出现本栈那一种调用名）：

```
dataset: FactOnlineSales
description: 线上销售明细，一行 = 一个订单行。未说明渠道的销售问题用这张表。
columns:
  - name: SalesAmount
    description: 销售额（美元）
  - name: PromotionKey
    description: 促销键；1 = 无折扣
relationships:
  - from: FactOnlineSales.CustomerKey
    to: DimCustomer.CustomerKey
    cardinality: 多对一
    use: 按客户或客户所在地分析时走这条
metrics:
  - name: 毛利率
    definition: (销售额 − 成本) ÷ 销售额
    callable: "[Gross Margin %]"   # 只在 L2 出现；SQL 单元写 MEASURE(...)，JSON 单元写指标名
```

L2 的指标就是这样暴露给 agent 的：写在上下文里的一份清单（名称、口径、调用名）。agent 在查询里引用名字，由 Power BI 或 Cube 的引擎计算。第一期不需要 MCP；探查 agent 的 run_sql 是唯一的工具。

## 企业约定清单（定稿）

你在 v4 上审过，没有补充；第 12 条按你的问题改了用词。下面 15 条是这家虚拟零售公司的业务规矩，代表需求调研时业务方会给的东西。所有 L1 及以上的单元拿到同一份；L0 和 R 拿不到，这正是「约定没写下来」的代价。

**渠道与事实表**

1. 未说明渠道的「销售、订单、退货、折扣、营收」指线上渠道。
2. 以门店为对象的问题（各门店、门店经理、同店、渠道对比、全渠道）用全渠道销售。全渠道销售按天、门店、产品、促销汇总，没有订单号。

**时间**

3. 数据截至 2009-12-31，以这一天为「今天」：今年 = 2009 年，去年 = 2008 年，上季度 = 2009 年第四季度。
4. 比较不同类型的日子（节假日与平日、周末与工作日、季节）时用日均销售：先按天汇总，再对天数求平均。

**地理与币种**

5. 按国家、地区、大洲分析销售时，默认按客户所在地；只有明确说「门店所在地」才按门店。
6. 金额一律为美元；线上销售已是美元，无需换算。

**口径与业务词**

7. 销售额、营收、GMV = 销售金额（已扣折扣、未扣退货）；净销售额 = 销售金额 − 退货金额；毛利 = 销售金额 − 总成本；毛利率 = 毛利 ÷ 销售金额；退货率 = 退货数量 ÷ 销售数量。
8. 订单 = 线上订单号；客单价（平均订单金额）= 销售额 ÷ 去重订单数。
9. 产品利润率、「最贵的产品」这类问题用产品表的标价和成本，不用成交价推算。
10. 促销键 1 表示「无折扣」；问折扣金额或促销效果时不计无折扣交易。

**库存、计划与销售目标**

11. 库存是每日快照，不能跨日期求和；「当前库存」取每个门店 × 产品最近一次快照。
12. 战略计划表按实体 × 品类 × 科目记金额，分实际、预算、预测三个场景；「收入」对应科目 Sale Revenue。销售目标表（数据里叫 quota，也常译作「配额」）记录分配给每家门店 × 产品 × 日期的目标销售额和目标销量，同样分三个场景，正式目标看预算场景。目标达成率 = 全渠道实际销售额 ÷ 预算场景的目标销售额。

**客户**

13. 按最近一次购买距 2009-12-31 的月数分层：6 个月内为活跃，7–12 个月为有流失风险，超过 12 个月为已流失。
14. 新客：首次购买日落在截止日前 90 天内的客户；首次购买指该客户有史以来第一次购买；截止日由问题的时间窗口决定（按月看就是每个月的最后一天）。
15. 同店口径：只比较两个对比年份都有销售的门店。

关于公正性：这份清单由看过题目的我起草，相当于「业务方」。它只写企业级规矩，不写任何一道题的解法，而且 L1 及以上各档拿到的完全一样，所以不影响 L1 以上各档之间的比较。它会抬高 L1 相对 L0 的差距，这部分提升是真实的：企业把约定写下来，就能拿到这些分。盲写 L1 的 agent 要逐条对照数据核实（比如科目名、场景编号），发现矛盾就标出来交给你。

## 假设与可执行结论

十个对比，每个都事先写好「结果是这样，就做那件事」。差距分三档：5 个点以内不解读，5–15 个点看方向，15 个点以上算大。约 105 道主题时单个准确率本身就有约 ±9 个点的波动；只用半数题的 C2 和各种分层结果标为探索性。

| # | 对比 | 回答什么问题 | 结果 → 决定 |
|---|---|---|---|
| C1 治理 | SQL：L0 → R → L1；DAX：L0 → L1 | 该不该先做数据治理，先做哪部分 | L0 → L1 大：先治理。L0 → R 就拿到大部分：先改命名。R → L1 才大：光改名不够，要写描述、枚举和约定。 |
| C2 通用 vs 调优 | L1 vs L1 调优、L2 vs L2 调优，只在留出题上比；L1c 在 Cube 原题与新题上的落差 | 一份通用文档够不够，还是要靠 bad case 持续调 | 留出题上也明显领先：调优能泛化，上线后要有收集点踩、迭代文档的流程。只在调优题上领先：调到的是题目本身，高频问题直接做成已验证答案更划算。都不明显：一次写好的通用文档够用。 |
| C3 宽表与汇总层 | SQL：L1 → L1.5W；L1 → L1.5S（汇总层覆盖内、覆盖外分开看） | 数仓现成的宽表和汇总表，对问数帮助多大 | 明细宽表提升大：问数直接接宽表，这是已有资产，几乎零成本。汇总层在覆盖内很高、覆盖外多为拒答：汇总层适合固定报表范围内的问题，范围外要退回宽表或指标层；覆盖外拒答多于错答是好结果。两者都小：杠杆在口径和约定，不在数据结构。 |
| C4 编码 | SQL：L1.5W → L2，L1.5S → L2；DAX：L1 → L2 | 已经有宽表和汇总表，还要不要建指标层或度量值。这正是很多企业现在在问的问题 | L2 比明细宽表明显更高且集中在 Q2/Q3：为高频组合口径（同比、占比、达成率、期末库存）建指标。L2 比汇总层高，主要高在汇总层覆盖外：指标层的价值是灵活组合，报表范围内的问题汇总层够用。都差不多：宽表加文档就够，不必为问数单独建指标层。 |
| C5 语言 | SQL L1 vs DAX L1；SQL L2 vs DAX L2 | 同样的信息，语言本身差多少 | L1 上 SQL 明显更高：问题超出度量值覆盖时，让 agent 退回数仓写 SQL。L2 上也有差：按差距选底座。都差不多：按现有技术栈选。 |
| C6 接口 | L2 上：DAX、SQL + MEASURE()、JSON | 指标建好后，用哪种接口让 agent 调用 | SQL 与 JSON 读同一个 Cube 模型、同一个引擎，二者之差全部来自接口：一是表达力（JSON 不能在指标结果上再算一步，SQL 可以），二是模型对这种语言的熟悉程度。失败归类里单列「接口表达不了」，把两者分开。再看「对 / 错答 / 拒答」的构成：错答率明显更高的接口，在财务这类错答代价高的场景，高风险口径只走「只能调用」的接口。 |
| C7 治理 vs agent | L0-E vs L0 vs L1；L1-E vs L1；L2-E vs L2；按题目的「语义依赖」分开看 | agent 能替代哪部分治理；有了指标层还要不要让 agent 查库 | 只在「可从数据发现」的题上追平 L1：改名、补枚举说明可以交给 agent，治理力气集中在约定和口径。两类题都追平：问数场景下治理的边际价值低，可以先投入 agent 能力，但要算上每次问数多花的 token 和时间。都追不平：治理是前提。L2-E 比 L2 高不到 5 个点：有指标层时不必给问数 agent 开查库权限，省掉 agent 税和权限风险。 |
| C8 剩余错误 | 失败归类 | 剩下的错误由谁解决 | 信息缺失类（调优能修的）：回到语义层。多步和统计类：靠 harness。接口表达不了、汇总层未覆盖：换接口或退回明细。理解类（读错题、选错字段）：第二期换更强的模型验证。 |
| C9 用户 | 管理层题 vs 分析师题 | 先对谁开放 | 管理层题在 L1 已经够高：先对管理层开放。分析师题差距大：分析师场景要 L2 或更好的 harness。 |
| C10 呈现格式 | DAX-L1 vs DAX-L1 原生 | 同样的信息，喂中立的 YAML 还是喂产品的原生格式 | 原生格式低 5 个点以上：给 agent 喂一份中立格式的导出（如 OSI），不要直接喂 TMDL。差不多：直接用产品的格式，省掉一层转换。 |

另有一项描述性分析：按复杂度来源 × 单元出一张准确率热力表，看哪个因素影响最大、哪个栈在哪类题上「撞墙」，见「查询复杂度映射」。工时照记（写 L1、建宽表、建汇总层、建指标、调优各多少小时），作为给读者的投入产出参考。

### 标签与划分

- **标签**：Q 级（以 L1 为准）、复杂度来源、语义依赖、用户类型（管理层 / 分析师）、题型（指标分析 / 维度查找 / 统计 / 开放式），以及「汇总层能否回答」。
- **语义依赖**：答对这道题需要哪些知识，分两类。「可从数据发现」：枚举值、连接键、取值格式，会查数据的 agent 自己能找到。「只能由业务告知」：约定、口径、业务词，数据里没有。C7 靠它把「治理 vs agent」拆开看。
- **汇总层能否回答**：语义层冻结后，由 Codex 判断每道题能否只用汇总表和维度表答出（以能否复现参考答案为准）。C3、C4 靠它把汇总层的覆盖内和覆盖外分开看。
- **复杂度来源的覆盖**：每类至少 8 道题，不足的由补题补齐。
- **划分**：按 Q 级 × 用户类型 × 题型分层，固定随机种子对半分成调优题和留出题。调优 agent 只拿到调优题中答错的那些加正确答案，相当于上线后用户点踩、分析师核实过的 bad case；留出题相当于用户还没问过的问题。

## 查询复杂度映射

复杂度衡量的是「语义层之外还剩多少计算要 agent 自己做」；「该知道什么」归另一个标签「语义依赖」。

- **Q1 直接**：一次汇总就能答，即已有指标或单列求和，加分组和筛选（含对汇总结果的筛选）。
- **Q2 组合**：在同一层汇总结果上再算一步（占比、增长、排名、累计），或把两个粒度对齐、对库存取期末。
- **Q3 嵌套或多步**：先在一个粒度上汇总，再把结果当成筛选条件或新维度，在另一个粒度上再汇总。

|---|---|---|---|---|
| 无，直接汇总 | Q6 2009 年线上销售总额；Q65 全渠道销售超过 500 万的门店经理 | Q1 | Q1 | 能 |
| 组合：比率 | Q24 各品类退货率 | Q2 | Q1 | 能，预先定义即可 |
| 组合：增长、累计、占比、排名 | Q77 逐月环比；Q23 累计月销售；Q78 促销类别折扣额及占比 | Q2 | Q1–Q2 | 部分：时间对比可以；占比、排名多数不行 |

| 筛选复杂度 | Q41 上季度销售；Q66 剔除无折扣交易；Q88 2009 年每个季度都买过的客户 | Q41、Q66 为 Q1；Q88 为 Q3 | Q88 仍是 Q3 | Q88 不能 |

Q65 的计算只是「按门店经理分组、过滤超过 500 万的」，属于 Q1；它难在语义：要知道「全渠道」用哪张表，而门店经理就是门店表上的一列。这类题的失败归到语义依赖，不归到复杂度。

滚动 90 天新客（你已确认）：截止日 T 的新客 = 首次购买日落在 T 前 90 天内的客户，首次购买指该客户有史以来第一次购买；T 由报表的时间窗口决定，按月看就是每个月的最后一天。什么都没有时是 Q3（先算每个客户的首购日，再按每个截止日数人头）；汇总层把首购日存为客户属性后是 Q2；「每个截止日往前数 90 天」随报表窗口变化，没法为任意窗口提前算好，所以你们放在 Power BI 用度量值算，那时就是 Q1。

**撞墙分析**：报告里出一张热力表，行是复杂度来源，列是 17 个单元，格子是准确率和题数。某个单元在某类题上低于 50%，或比它自己的平均低 20 个点以上，就标为「撞墙」。每类至少 8 道题，所以这张表只看方向，不看小差异。

## Harness 与评分

### 一次作答怎么跑

1. **系统提示**：角色；输出格式（一个查询代码块，加一行以「假设：」开头的说明；答不了就输出 CANNOT_ANSWER）；本栈的语法要点，各栈写成等长。
2. **语义上下文**：本单元对应档位的 YAML（DAX-L1 原生为 TMDL 与 AI instructions 原文）。同一单元内对所有题完全相同，放在最前面，可以命中缓存。
3. **用户消息**：一道中文问题。直答单元不给样例数据。
4. **执行**：报错时把报错信息发回去修正一次；修正前的结果单独记录。不因为答案错而重试。
5. **探查 agent**：可以先调 run_sql 查枚举值、看样例行、试跑查询（只读，每次最多 50 行、30 秒超时，最多 8 步），最后交一条查询。另记每题的步数、token 和耗时，即「agent 税」。

### 模型设置

- 第一期只用一个模型，由最小样本试跑选定（见下一节）。日志记录接口返回的确切版本。
- 思考模式开启（默认，强度 high）；思考模式不支持 temperature，所以每题独立跑 3 次。
- 系统提示在试跑后冻结，所有单元一致；试跑只修 bug，不按题调。

### 评分

- **自动比对执行结果**：数值相对误差 0.5% 以内；不看列名和列顺序，多出的列不扣分；问句要求排序或前 N 名时才比行序；边界并列任一都算对；小数与百分数等价；比对完整结果集；与任一可接受解读的参考答案一致即算对。
- **每次作答的结果是四种之一**：对；错答（给出了不对的数）；执行失败（修正后仍报错）；拒答。只有「对」记 1 分，其余三种都记 0 分。
- **准确率** = 答对的作答次数 ÷ 全部作答次数（题数 × 3）。等价于先算每道题 3 次的平均分（0、1/3、2/3 或 1），再对所有题求平均。
- **四种结果的占比加起来是 100%**，每个单元都报。其中**错答率**最要紧：它是「给出一个看起来像样的错数」的比例，对业务的伤害大于拒答。错答里再标出「已声明假设、偏差可见」的那些。
- **拒答在准确率里不加分**。但汇总层和 JSON 接口在能力范围外拒答是正确行为，所以这两个单元另报「覆盖外的拒答率」和「覆盖外的错答率」。
- **统计类和开放式**：自动比对之外，用 V4 Pro 做宽松判定，裁判拿到可接受解读清单；你抽检 20%。如果被测模型也是 Pro，就是自己评自己，报告里注明。
- **失败归类**：选错表或字段、路径错、口径错、筛选错、粒度错、语法错、接口表达不了、汇总层未覆盖、读错问题、拒答。只归类每个单元第一次运行的失败，V4 Pro 初判，你抽检。

### 报告什么

每个单元报告：准确率（3 次平均）、首次即对率（修正前，和 Cube 口径一致）、三次全对率、错答率、执行失败率、拒答率；再按 Q 级、复杂度来源、语义依赖、用户类型、汇总层覆盖分层。探查 agent 另报每题平均步数、token 和耗时。不做显著性检验。

### 花模型费之前的两步校验

1. **数据一致**：在我们导入的数据上逐题执行 Cube 的参考 SQL，与它公布的参考结果核对行数和数值。
2. **评分器一致**：用我们的评分器给 Cube 公布的 600 条候选 SQL 打分，与它公布的判定逐条对比，不一致的都要解释。

五个检查点，没过就不进入下一步：

- **G0 数据与评分器一致**：两步校验通过。
- **G1 语义层冻结**（tag `semantic-v1`）：L1、明细宽表、汇总层、指标清单、L0、渲染器都完成。此后 Claude Code 才能打开题库。
- **G2 题集冻结**（tag `eval-v1`）：参考答案经两家独立核对，划分和覆盖标注完成。
- **G3 模型选定、harness 冻结**（tag `harness-v1`）。
- **G4 结论审定**。

**Mac 能不能跑 Power BI Desktop**：不能原生跑，微软没有 Mac 版。Apple 芯片的 Mac 可以用 Parallels 装 Windows 11 ARM 版，再装 Desktop：今年 7 月有人实测可用，微软对 Windows on ARM 有条件地支持，但虚拟机要给 8 GB 内存，偶有首次打开失败。第一期你有 Windows 电脑，不需要它。第二期测境外模型时它有用：如果那台 Windows 连不上境外模型，虚拟机走 Mac 的网络，就不必拆成「Mac 调模型、Windows 执行」两台机器。

## 分工：Claude Code 与 Codex

按「谁在什么时候能看到题」分，而不是按仓库分；结果大致是一家管一个仓库。这些规则已经写进两个仓库的 AGENTS.md、任务总览和每张卡，你不用记，也不用转述。

1. **Codex 管题库**：引入外部基准文件、审计落地和数据校验、中文化与标注、补题、划分与冻结；另外承担需要「另一家」来做的独立工作：评分器、指标层（Cube）、报告数字复核。它从一开始就能看到题。
2. **Claude Code 管语义层、渲染器、harness 和全部运行**。在 G1 之前，它的每张卡都按盲任务启动，看不到题库；G1 之后才打开题库。盲任务有可强制的读隔离（见下一节），所以盲任务都给它。
3. **独立核对跨厂商**：参考答案由 Codex 写 SQL，Claude Code 在 G1 后用 pandas 重算；评分器由 Codex 写，harness 由 Claude Code 写；报告数字由 Codex 从原始日志重算。同一家的两个会话容易犯同样的理解错误，所以核对要换一家。
4. **子 agent 可以用**，用来并行做卡内可以拆开的活：分批改写题目、分表做数据探查、并行写测试。子 agent 和主 agent 在同一个目录、同一套权限下工作，隔离不受影响。但「独立核对」和「调优的 B 角」不能交给子 agent：子 agent 的指令是主 agent 写的，会把主 agent 的理解带过去。子 agent 也不得直接调用 DeepSeek。
5. **你只需要说「执行任务卡 Txx」**。agent 开工前先自检：自己是不是这张卡的负责方、依赖是否满足、是否在正确的目录和模式下启动；不对就停下，告诉你正确的启动命令。

## 仓库与启动

两个仓库是两个并列的文件夹，不再用子模块。v4 的子模块只是主仓库里的一个指针，题库内容从来不在主仓库里；但它让人困惑，也不是隔离所必需的，所以去掉。主仓库的程序通过环境变量 `SEMDEBT_EVAL_DIR` 找到题库，每次运行把题库的提交号写进日志，同样可以复现。

目录布局是固定的，脚本和权限设置都按它写：

```
~/semdebt/
  semantic-debt/        主仓库（你的主工作区，合并用）
  semantic-debt-eval/   题库仓库（Codex 在这里工作）
  cards/T08/ …          每张卡一个独立的 clone，agent 在里面工作
  data/                 数据（SEMDEBT_DATA_DIR），不进任何仓库
```

**隔离怎么生效**：主仓库提交了一份 Claude Code 项目设置，打开沙箱，并禁止读取工作目录以外的文件；数据目录单独放行。盲模式的卡在自己的 clone 里启动，题库在工作目录之外，读不到；G1 之后的卡用普通模式启动，题库目录被显式加进来。T00 要在你的 Mac 上逐项验证：读题库被拒、跑测试和读数据正常、能提交。

**先建 GitHub 还是本地**：都可以。你已经在 GitHub 上建好了，就以 GitHub 为准：每张卡的 clone 从 GitHub 拉，改动以 PR 的形式在 GitHub 上合并。只用本地也行：两个文件夹各自 `git init`，以后再 `git remote add` 推上去。

开工步骤（完整版在主仓库的 `START-HERE.md`）：

1. 建目录，把两个仓库克隆下来；解压种子包，复制进去，提交并推送。
2. 从 Kaggle 下载数据，放到 `~/semdebt/data/raw/`：[Cleaned Contoso Dataset](https://www.kaggle.com/datasets/bhanuthakurr/cleaned-contoso-dataset)。
3. 在 `~/.zshrc` 里加三个环境变量：`SEMDEBT_DATA_DIR`、`SEMDEBT_EVAL_DIR`、`DEEPSEEK_API_KEY`（最后一个到 T11 再加）。
4. 启动第一张卡：`cd ~/semdebt/semantic-debt && claude "执行任务卡 T00"`。
5. 之后每张卡都用 T00 写好的脚本启动：`~/semdebt/semantic-debt/scripts/start-card.sh T08`。它会建好这张卡的 clone、放好对应模式的设置，然后打印该用 Claude Code 还是 Codex、在哪个目录启动。

## 费用

选 Flash 时全部模型费约 210 元，选 Pro 时约 550 元（都按错峰时段，高峰翻倍）。钱主要花在思考输出和探查 agent 的多轮调用上。

| 部分 | 单元 | 作答次数（每题 3 次） | 模型调用 | Flash | Pro |

| SQL 直答 | 8 个中文单元 × 120 题 + 2 个英文锚点 × 99 题 | 3,474 | 约 3,820 | 约 50 元 | 约 167 元 |
| SQL 探查 agent | 3 × 120 题 | 1,080 | 约 6,480（每题约 6 步） | 约 56 元 | 约 210 元 |
| 指标层 JSON | 1 × 120 题 | 360 | 约 400 | 约 5 元 | 约 18 元 |
| DAX | 5 × 120 题 | 1,800 | 约 1,980 | 约 28 元 | 约 92 元 |
| 最小样本试跑 | 2 个单元 × 24 题 × 2 个模型 | 288 | 288 | 约 8 元（两个模型合计） | 同左 |
| 裁判与失败归类（Pro） | — | — | 约 1,600 | 约 60 元 | 约 60 元 |
| 合计 | 17 个中文单元 + 2 个锚点 | — | 约 14,600 | **约 210 元** | **约 550 元** |

假设：直答每次输入约 1 万 token（95% 是同单元共用、可命中缓存的前缀）、输出约 3,000 token；探查 agent 每步输入约 1.5 万 token、输出约 1,500 token；报错修正加 10%；DAX-L1 原生的上下文按 YAML 的 1.3 倍估。裁判与归类约 1,600 次 = 各单元第一次运行的失败约 790 次，加统计和开放式 14 道题在 19 个单元各 3 次的宽松判定约 800 次。最大的不确定项是思考输出的长度，试跑后用实测值替换。

## 最终报告必须写到的

- **主问题的说法**：「已经有宽表和汇总表，还要不要建指标层」。这是很多企业现在正在问的问题，C3、C4 直接回答它。
- **OSI**：统一 YAML 与 Open Semantic Interchange 的关系，以及 C10 的结果对「给 agent 喂什么格式」意味着什么。
- **三种作答方式的定义**（直答、探查 agent、规划 agent）和 agent 税。
- **投入产出**：各档的工时与准确率提升并列。
- **局限**：一个模型、约 25 张表、中文问句；Contoso 本身很干净，真实的坏交付比 L0 更坏。

## 第二期、第三期与不在范围内

第一期的结论限定在「约 25 张表的零售模型、中文问句、一个 DeepSeek 模型、直答加一种探查 agent」。下面的都能在第一期的仓库上直接加。

**第二期**（按优先级）

1. **规划 agent（-P）**：规划、Python 退路、按需检索，以及用 MCP 接入的工具，与第一期的直答、探查 agent 对比。
2. **模型**：Flash、Pro、Qwen、Claude、GPT；包括用更强的模型修第一期剩下的「理解类」错误。境外模型：Windows 连不上时，用 Mac 上的 Parallels 虚拟机跑 Desktop，或「Mac 调模型、Windows 执行」两台机器拆分。
3. **本体与约束校验**：生成的查询先过规则（库存不跨期求和、计划与实际先对齐粒度），不通过就打回。
4. **上下文范围与呈现**：AI 数据 schema 式的字段裁剪、约 600 个字段的噪音版、Power BI MCP 输出的 schema、SQL 侧的原生格式（建表语句加注释）。
5. **Contoso 缺的陷阱**，优先做你们的场景：客人的主属门店和主属导购（main store、main SA）及其业绩归属规则，用「加列不改行」的方式给客户表加属性，再出一组「按主属门店 vs 按交易门店」的题。其后是日期角色、订单取消、缓慢变化维度、零售 4-5-4 财历。
6. **歧义与追问**：agent 该追问时是否追问。
7. **中英文问句对比**。

**第三期**：统计严谨性，扩题到约 200 道、做配对检验。只在你想发论文时做。
