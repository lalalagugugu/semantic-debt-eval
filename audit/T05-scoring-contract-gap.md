## 最小反例（纯合成数据）

业务要求每店一个赢家，两家店各有两个并列赢家：

| store | product | sales |
|---|---|---:|
| A | A1 | 100 |
| A | A2 | 100 |
| B | B1 | 100 |
| B | B2 | 100 |

参考保存完整边界。正确候选A1+B1；错误候选A1+A2（漏B店）。实际现有评分器结果：

| 输入规则 | 候选 | 结果 |
|---|---|---|
| ordered=false, top_n=null | A1+B1 | wrong / row_count：要求与4行完整参考等长 |
| ordered=true, top_n=2, tie_columns=[sales列] | A1+B1 | correct |
| 同上 | A1+A2 | correct：全局同额集合没有分组覆盖/唯一性约束 |

复现命令（设置SEMDEBT_MAIN_DIR）：

```bash
uv run --locked python scripts/check_grouped_topn_contract.py
```

该诊断退出0表示成功复现缺陷，不表示评分契约通过。它只读导入现有harness/scorer.py和value_units.py，不修改主仓库，不访问数据库、模型或网络。

## 对真实数据的核实

只读分析已提交、已全量复验的Q74参考（2009年全渠道每店产品销售，含完整统一量化边界），与新版Q119的局部赢家域一致：306个门店，4店第一名并列，最大并列数2；每店择一共有16种完整结果集合。

因此并列并非纯假设。只选一个参考赢家会误杀合法答案；把所有赢家直接当完整无序行集会要求候选也交所有赢家；强套全局N则可能漏店而判对。

## 已检查的替代路径

1. **主评分器保持原样，随便填top_n=null或全局N**：反例证明不可行，不能当元数据补全解决。
2. **按StoreKey/ProductKey强行打破并列**：把冻结的“边界任选”改成指定唯一答案，不采用。
3. **枚举所有合法候选行集**：这份数据的Q119局部选择只有16种，资源上不是不可行；但每份枚举结果不再是完整边界参考，且现有管道没有通用的“保存完整边界→按组展开合法行集”契约。不能把枚举当不同业务解读，或用top_n=null隐去分组要求后声称契约已补齐。若采用这一通用适配路线，也应先批准契约、测试其组合规模及完整边界保存方式，而非临时逐题手工列答案。
4. **改走judge**：此前候选/草稿建议过这一方向，但原设计只明确统计和开放式的宽松judge。把Q117/Q119指标分析题改为judge-only，会改变主分析的评价路径，不能由我在题库内悄悄实施。尚无经验证的通用分组judge契约；声明了口径也不能证明对象数/成员正确。

## 推荐决策

保留已接受题目和冻结评分原则，批准先补**通用分组/嵌套Top-N评分输入契约与确定性实现**：

- 表达各选择阶段的对象身份、分组范围、N、排名方向及量化排序键；前一阶段选择影响后一阶段的合法域。
- 参考保存严格前缀及完整边界；候选仍按各阶段要求恰好选择N个对象，不得漏组、重复对象或交N+k冒充N。
- 用不含题目内容的合成测试覆盖缺组、重复组、边界合法任选、完整边界超交、嵌套选择等；不按题号设分支，不调整容差，不修改系统提示或语义层。
- 主仓库仅放通用代码、合成测试和不含题干的契约；题目、参考SQL和结果仍只在题库。

这超出T05题库改动范围，须用户明确批准后才进入主仓库相关工作。另一选择是用户明确批准扩展指标分析的judge评价路径，但不推荐以此替代可确定性核验的排名约束。
