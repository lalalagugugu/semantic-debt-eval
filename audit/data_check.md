## 结论

从 Parquet 强制重建 `chdb-eval` 后，25 张表共 34,326,191 行，与 T01
导入报告一致。100 道外部参考 SQL 的校验结果是：

- 87 题与公开参考的行数和数值直接一致。
- 9 题（Q04、Q13、Q14、Q20、Q21、Q34、Q35、Q37、Q47）的公开工件固定只保存
  100 行；本地完整行数更多，公开的 100 行逐行都是本地完整结果的子集。这是公开工件截断，
  不是数据漂移。
- 3 题（Q79、Q85、Q88）的行数和排序值一致，但 SQL 在 Top-N 边界没有稳定
  tie-break，公开环境和本地环境从同值并列组中选出了不同成员。这是参考 SQL 的确定性问题，
  不是数据漂移；冻结前须按已经裁决的完整边界并列规则处理。
- Q33 在公开服务器的 30 秒限制下超时、没有公开结果；本地不设时限，89.457 秒成功返回
  20 行。
- 公开参考为 0 行的 Q39、Q49 在本地也都是 0 行。
- 因此，底层数据不一致题为 **0**；所有 13 个非直接一致项都有可复现解释。

公开结果中的 Q44 首行是非有限浮点数。公开 Python 工件保存为 `Infinity`，chDB 的 JSON
格式默认写成 `null`；用 CSV 复核本地值实际为 `inf`，其余有限数值均在 0.5% 容差内。
校验脚本启用 `output_format_json_quote_denormals` 后将其规范化，因此 Q44 计为一致。

## Q30 转交项：公开 G-R 窗口值为何与本地重执行不同

结论：差异来自外部执行工件，而不是数据漂移，也不是 `DimDate` 重复行造成的 join 扇出。

证据：

1. 参考 SQL 在本地返回 31 行，逐值与公开参考的 31 行一致。
2. 原样重执行公开 G-R Q30 SQL，本地 31 行逐值与参考结果一致。
3. 2009 年 12 月的 `DimDate` 是 31 行、31 个唯一日期，排除了公开 judge 所猜测的
   “LEFT JOIN 引入额外行”。
4. 公开 G-R 工件首行的日销售额为 2,044,409.8944，但同一行的 7 日移动平均为
   2,160,684.2123。`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` 的第一行没有前驱，
   移动平均必须等于当天值；公开工件违反了自身 SQL 的窗口语义。相对差异约 5.38%。
5. 本地原样重执行的首行移动平均为 2,044,409.8944，满足窗口语义并与参考一致。

因此可以把根因定位为：公开 G-R Q30 的“SQL + rows”工件不是该 SQL 在正确窗口语义下的
可复现结果，问题位于外部执行环境或工件生成过程。vendored 工件没有保存远端 ClickHouse
版本、查询计划或执行日志，无法再区分远端引擎/版本缺陷与写入了陈旧结果；现有证据足以排除
本地数据、参考 SQL 和维表重复。该不确定边界必须保留，不能臆测成某个具体引擎 bug。

## 复现

先从 Parquet 重建独立数据库：

```bash
cd "$SEMDEBT_MAIN_DIR"
uv run python data/build_chdb_copy.py "$SEMDEBT_DATA_DIR/chdb-eval" --force
```

再在题库仓库执行校验。T03 第二步建立本仓库 uv 环境之前，暂用主仓库已锁定的 chDB 环境：

```bash
cd "$SEMDEBT_EVAL_DIR"
uv run --project "$SEMDEBT_MAIN_DIR" python scripts/check_vendor_refs.py \
  --output /tmp/t03-data-check.json
```

机器可读结果只写入 `/tmp`，提交的报告保留题号、行数和诊断，不提交原始数据。
